\begin{abstract}
The integration of Large Language Models (LLMs) into software development workflows has significantly accelerated code generation and debugging; however, these systems frequently suffer from "contextual amnesia", the inability to retain architectural decisions, user preferences, and high-level design intent across disconnected development sessions. This paper presents Contextware, a persistent semantic memory skill developed for the Gemini CLI that addresses these limitations through a localized, three-tier memory architecture.

Contextware utilizes a local vector database (LanceDB) and CPU-efficient embeddings (FastEmbed) to manage three distinct data collections: a "Hippocampus" for explicit developer facts and constraints, a "Diary" for historical conversation logs, and a "Map" for a semantically indexed codebase. A novel contribution of this work is the implementation of an autonomous background indexing mechanism that employs "headless" agent instances to recursively summarize file purposes and symbol structures without interrupting the primary developer workflow. By combining proactive memory capture with a robust Retrieval-Augmented Generation (RAG) pipeline, Contextware enables CLI agents to maintain a consistent project "mental model," significantly reducing the need for manual context re-provisioning. Preliminary results demonstrate that this architecture improves agent autonomy in complex refactoring tasks and ensures long-term adherence to project-specific conventions, providing a scalable blueprint for more reliable autonomous engineering systems.


Keywords: Semantic Memory, Autonomous Agents, Software Engineering, Retrieval-Augmented Generation (RAG), Large Language Models, Vector Databases.
\end{abstract}

\section{Introduction}

The emergence of Large Language Models (LLMs) has catalyzed a paradigmatic shift in software engineering, transitioning from syntax-level autocompletion to the deployment of \textbf{autonomous agents} capable of resolving real-world GitHub issues. As the field moves from simple code generation to \textbf{intent abstraction} \cite{Xu2025Memory}, agents are increasingly expected to act as "deep agents" that automate complex, long-duration business processes. However, as these agents move from statement-level generation to repository-level problem solving, they encounter a fundamental bottleneck: \textbf{agent amnesia}.

\subsection{The Context Window Bottleneck}
Autonomous coding agents are currently restricted by the \textbf{fixed context windows} of Transformer architectures. While recent advancements have expanded these limits to millions of tokens, the self-attention mechanism's \textbf{quadratic complexity $O(n^2)$} \cite{Nan2025Nemori:} makes simply increasing the context window prohibitively expensive in terms of latency and computational cost. In professional software development, interactions with a codebase can span weeks, months, or even indefinitely. Holding the entire historical context within a single prompt is not only computationally unsustainable but also introduces significant noise that hinders the agent's ability to focus on task-relevant information.

\subsection{The Engineering Gap and Multi-Hop Reasoning}
Professional coding is uniquely memory-intensive. Real-world repositories, such as those represented in the \textbf{SWE-bench} framework, average 438,000 lines of code across thousands of files \cite{Jimenez2023SWEbench}. Resolving a single bug often requires \textbf{multi-hop reasoning}---the ability to synthesize information dispersed across multiple functions, classes, and modules defined in disparate development sessions. Standard models often suffer from the \textbf{``lost in the middle'' phenomenon} \cite{Jimenez2023SWEbench} \cite{Nan2025Nemori:}, where attention degrades for information buried in the center of a long prompt. This manifests as \textbf{memory inflation}: the linear accumulation of raw logs increases token costs and latency while simultaneously introducing irrelevant context that leads to self-degradation and error propagation \cite{Xu2025Memory}.

\subsection{Operational and Economic Bottlenecks}
The failure to manage memory is not merely a technical limitation but an operational one. Without a persistent memory mechanism, agents are forced to ``re-learn'' repository structures and developer preferences in every new session. This leads to a state of \textbf{contextual degradation}, where the accumulation of flawed or irrelevant memories causes the agent's performance to decline over time \cite{Xu2025Memory}. Furthermore, the economic cost of re-sending hundreds of thousands of tokens of repository context for every sub-task request makes autonomous agents impractical for large-scale enterprise deployment.

\subsection{Contributions of Contextware}
To bridge this gap, we introduce \textbf{Contextware}, a memory-augmented skill for the Gemini CLI that shifts the agent from passive logging to \textbf{proactive, tiered memory management}. The specific contributions of this work include:
\begin{itemize}
    \item A \textbf{three-tier storage hierarchy} (Hippocampus, Diary, and Map) inspired by the Common Model of Cognition to segregate persistent constraints from historical task logs.
    \item An \textbf{autonomous background indexing engine} that utilizes headless agent instances to recursively summarize file intent and repository structure without interrupting the primary user workflow.
    \item A \textbf{structural symbol navigation} module that uses Abstract Syntax Tree (AST) parsing to extract class signatures and method maps, ensuring the semantic integrity of retrieved code.
    \item A design optimized for \textbf{local deployment} using LanceDB and FastEmbed, ensuring developer privacy and millisecond-level retrieval latency.
\end{itemize}

\section{Background}

The development of Contextware is rooted in a synthesis of cognitive science, systems engineering, and natural language processing to solve the foundational challenge of agent amnesia established in the previous section. This section provides an exposition of the cognitive frameworks used to model persistent intelligence, the operational lifecycle of agentic memory, and the technical limitations of existing retrieval systems when applied to complex software engineering tasks.

\subsection{Cognitive Memory Frameworks}
To simulate human-like persistence and overcome the amnesia established in our Introduction, researchers have turned to the \textbf{Common Model of Cognition (CMC)} \cite{Hatalis2024Memory}. The CMC posits that a functional intelligent agent must segregate information based on its temporal and conceptual nature rather than treating interaction logs as a monolithic stream \cite{Zhang2024A}. Contextware adopts this tripartite approach to memory storage:
\begin{itemize}
    \item \textbf{Working Memory (WM)}: Functionally represented by the immediate context window, this tier is populated with the situation description required to drive the agent's current prompt \cite{Hatalis2024Memory}.
    \item \textbf{Semantic Memory (SM)}: Represents accumulated factual knowledge and abstract concepts that remain independent of specific events \cite{Xu2025A-MEM:}. In the coding domain, this includes project-wide architectural constraints and developer-specific preferences.
    \item \textbf{Episodic Memory (EM)}: A narrative log of past temporal experiences, recording ``what happened when'' \cite{Wang2025MIRIX:}. This allows the agent to recall specific past successes and, crucially, avoid re-attempting failed sub-tasks \cite{Xu2025Memory}.
    \item \textbf{Procedural Memory (PM)}: Stores actionable skills and structural maps of the environment \cite{Zhang2024CodeAgent}. For Contextware, this is realized as a semantically indexed map of the codebase.
\end{itemize}

\subsection{From Static Retrieval to Dynamic Experience}
The transition from Retrieval-Augmented Generation (RAG) to \textbf{Memory-Augmented Generation (MAG)} represents a fundamental shift in how LLMs interact with data \cite{Nan2025Nemori:}. Traditional RAG systems were designed for static knowledge bases and operate on a \textbf{``stateless information patch''} philosophy \cite{Nan2025Nemori:}. While effective for finding localized facts, these systems are misaligned with the needs of an autonomous agent for three reasons: (1) their reliance on offline indexing prevents real-time learning; (2) their focus on document similarity ignores the temporal nature of dialogue; and (3) their use of \textbf{arbitrary fixed-size chunking} often leads to \textbf{semantic fragmentation} \cite{Nan2025Nemori:}. 

In a software repository, fragmentation occurs when a single class or method is split across multiple vector chunks, destroying the agent's ability to perceive the logical integrity of the code. MAG architectures, by contrast, emphasize the \textbf{autonomous self-organization} of an agent's own lived experience into optimized, coherent representations \cite{Nan2025Nemori:} \cite{Salama2025MemInsight}.

\subsection{The Operational Lifecycle: Writing, Management, and Reading}
An effective persistent memory must facilitate a complete lifecycle of operations to prevent the knowledge base from becoming a haphazard pile of raw text \cite{Zhang2024A} \cite{Chhikara2025Mem0:}.
\begin{enumerate}
    \item \textbf{Memory Writing}: This is the process of \textbf{proactive information extraction}. Rather than passively logging every token, the agent must identify and distill salient facts and event summaries for storage \cite{Chhikara2025Mem0:}.
    \item \textbf{Memory Management}: This involves resolving conflicts and maintaining consistency. As will be discussed in the Relevant Works section regarding Mem0, this requires operations such as \texttt{ADD} for new information, \texttt{UPDATE} for augmenting existing knowledge, and \texttt{DELETE} for removing contradicted facts \cite{Chhikara2025Mem0:}.
    \item \textbf{Memory Reading}: This utilizes \textbf{active retrieval} to prevent the model from defaulting to its internal parametric knowledge, which may be outdated or incorrect \cite{Wang2025MIRIX:}.
\end{enumerate}

\subsection{Scalability and the Logic of Forgetting}
As an interaction history grows over weeks or months, agents suffer from \textbf{memory inflation}, where the accumulation of irrelevant or redundant data leads to exponential increases in token costs and latency \cite{Xu2025Memory}. Without a management mechanism, this leads to \textbf{contextual degradation}, a state where the agent begins to contradict its own previous decisions or repeat errors due to ``misaligned experience replay'' \cite{Xu2025Memory}.

To ensure lifelong learning, agents must implement \textbf{intelligent forgetting} or \textbf{intelligent decay} \cite{Kang2025Memory} \cite{Xu2025Memory}. Inspired by the biological principle that memory utility is a function of engagement, systems assign a \textbf{Utility Score} $S(M_i)$ to each memory entry. This score is typically a composite of \textbf{Recency} (time-decay), \textbf{Relevance} (semantic similarity), and \textbf{Frequency} (access counts) \cite{Kang2025Memory} \cite{Kang2025Memory}. High-utility ``hot'' memories are retained in faster tiers, while ``cold,'' low-utility memories are consolidated into compact summaries or evicted entirely to maintain system efficiency.

\subsection{Memory Requirements for Repository-Level Reasoning}
The complexity of repository-level software engineering tasks, such as those represented in the \textbf{SWE-bench} framework, places unique demands on an agent's memory \cite{Jimenez2023SWEbench}. Success in this domain hinges on \textbf{multi-hop reasoning}---the ability to synthesize information dispersed across thousands of files and disparate development sessions \cite{Jimenez2023SWEbench} \cite{Anokhin2024AriGraph:}. 

For example, an agent must bridge the gap between a high-level requirement defined in session A and a specific utility function implemented in session B to solve a bug in session C. Standard vector retrieval often suffers from \textbf{relational blindness} in these scenarios . This gap necessitates the \textbf{structural symbol navigation} and \textbf{recursive background indexing} approaches that Contextware implements to maintain a global ``mental model'' of the project without overloading the immediate context window.

\section{Relevant Works}
Current research has transitioned from linear text logs to structured and proactive memory management architectures.

\subsection{Structural Paradigms: Graphs and Hierarchies}
Several recent works emphasize the importance of structured representation for complex reasoning. AriGraph integrates semantic factual triplets and episodic experience edges within a world model graph, significantly improving spatial orientation and multi-hop reasoning in text-based environments \cite{Anokhin2024AriGraph:}. Mem0 and its variant Mem0G utilize graph-based representations to capture complex relational structures, achieving superior accuracy in temporal and open-domain tasks compared to unstructured memory \cite{Chhikara2025Mem0:}. A-MEM draws inspiration from the Zettelkasten method, using interconnected atomic notes that evolve over time as new memories are integrated, allowing the system to refine its contextual understanding \cite{Xu2025A-MEM:}. While these \textbf{structured memory techniques} provide significant performance gains for particular workflows, their complexity can lead to higher latency and error accumulation during graph construction \cite{Chhikara2025Mem0:}.

\subsection{Operating System-Inspired Architectures}
Other architectures utilize principles from computer operating systems. \textbf{MemoryOS} introduces a three-tier storage hierarchy comprising short-term, mid-term, and long-term personal memory. It employs \textbf{segmented paging} and \textbf{heat-based eviction} strategies based on access frequency and recency, demonstrating that mid-term topic summaries have the highest impact on maintaining dialogue coherence \cite{Kang2025Memory}. \textbf{MemGPT} also treats memory like an operating system with a ''RAM/Disk'' analogy, using self-directed function calls to page information in an d out of the limited context window. These hierarchical tiers ensure that topic-aligned content remains accessible while maintaining consistency with user-specific preferences \cite{Packer2023MemGPT}.

\subsection{Proactive Learning and Multimodal Integration}
Moving beyond passive extraction, Nemori introduces the Predict-Calibrate Principle, where the agent forecasts its own experience and only distills new knowledge from the surprise or prediction gap against the raw interaction \cite{Nan2025Nemori:}. MemInsight autonomously mines and prioritizes semantic attributes like user intent and emotion, which significantly improves recall compared to raw text similarity \cite{Salama2025MemInsight}. For multimodal contexts, MIRIX manages memory across six specialized components, including a secure Knowledge Vault for verbatim sensitive data and a Resource Memory for full documents, and can process thousands of screenshots to build a visual activity history \cite{Wang2025MIRIX:}.

\subsection{Specialized Coding Agents and Multi-Agent Teams} In the domain of software engineering, specialized agents leverage memory to handle repo-level tasks. \textbf{CodeAgent} formalizes repository-level code generation by integrating tools for \textbf{symbol navigation} and documentation reading into its agentic workflow \cite{Zhang2024CodeAgent}. \textbf{RepairAgent} is the first autonomous agent specifically for \textbf{program repair}, using a \textbf{finite state machine} to guide the model through gathering information and searching for repair ingredients \cite{Bouzenia2025RepairAgent}.
Furthermore, the research community is increasingly interested in \textbf{multi-agent coding teams}. \textbf{MetaGPT} incorporates \textbf{Standardized Operating Procedures (SOPs)} into agent collaboration by encoding role specialization (e.g., Architect, Engineer, QA) into structured prompt sequences. \textbf{ChatDev} utilizes a \textbf{``chat chain''} workflow where specialized agents engage in multi-turn dialogues to autonomously craft solutions, effectively reducing coding hallucinations \cite{Hong2023MetaGPT} \cite{Qian2024ChatDev}. While these multi-agent environments are a high-interest area for future investigation, the current implementation of \textbf{Contextware} focuses on a single-agent architecture to minimize synchronization overhead and manage complexity within the project's scope.

\subsection{Key Design Takeaways for the Project}
The following insights from the research are critical for implementing an efficient agent memory:

\begin{itemize}
    \item \textbf{Segregation of Memory Types}: Procedural, episodic, and semantic memories should be stored in separate structures to prevent internal contradictions and improve retrieval precision.
    Intelligent Decay Mechanism: A utility score based on recency, relevance, and user feedback must be implemented to prune irrelevant information and avoid performance decline caused by catastrophic interference.
    \item \textbf{Active Retrieval}: Instead of waiting for explicit triggers, the agent should self-generate a current topic to search memory proactively, preventing it from defaulting to outdated internal knowledge.
    \item \textbf{Human-in-the-Loop Transparency}: Providing a visual interface where users can pin important facts or delete flawed memories enhances reliability and user trust, particularly in business processes.
    \item \textbf{Semantic Attribute Mining}: Annotating raw data with autonomously mined attributes is more effective than relying solely on raw text embeddings for retrieval.
\end{itemize}

\section{Integration of Memory Architecture Insights}

The integration of Contextware into the Gemini CLI is based on moving the agent away from a simple text-search approach and toward a structured, reliable memory system. We have built the codebase to follow the specific requirements for long-term memory in AI agents, ensuring that the information retrieved is always useful and never confusing. Our system treats memory as a managed lifecycle where information is categorized, validated, and updated as the project grows.

\subsection{Code-Level Segregation of Memory Buckets}
The most important part of our integration is the physical separation of data into three distinct "buckets." In the \texttt{db.py} file, we define three specific models: \texttt{Fact}, \texttt{Episode}, and \texttt{CodeIndex}. These are not just labels; they are separate tables in the database. This design is a direct response to the problem where agents get confused by mixing different types of information in one single list.

The \texttt{facts} bucket is designed for project-wide rules. Each record has a \texttt{content} field for the rule and a \texttt{timestamp} to show when it was added. The \texttt{episodes} bucket tracks the history of work, including a \texttt{goal}, a \texttt{result} (success or failure), and a \texttt{summary} of the actions taken. Finally, the \texttt{code\_index} bucket maps out the project's structure. By separating these into different tables, our \texttt{recall.py} script can target exactly what the agent needs. For instance, if the agent asks for a project rule, the search only looks in the \texttt{facts} table. This prevents old, irrelevant chat history from the \texttt{episodes} table from showing up and giving the agent the wrong idea. This separation ensures the agent's "mental model" stays clean and accurate.

\subsection{Failure Prevention Logic in Recall}
To solve the problem of agents getting stuck in "infinite loops"—where they try the same failed strategy over and over—we implemented a specific search pattern in \texttt{recall.py}. Before the agent starts any new high-level task, it is programmed to search the \texttt{episodes} bucket for its current \texttt{goal}. The script looks specifically for past episodes where the \texttt{result} field was set to "failure."

When a failure is found, the script doesn't just give the agent raw logs; it provides the \texttt{summary} of that past attempt. This summary acts as a "lesson learned." For example, if the agent previously failed to fix a bug because it was looking in the wrong file, the \texttt{recall.py} script will find that failure and warn the agent about it before it even begins the new attempt. This logic is a mandatory step in our retrieval loop. It forces the agent to acknowledge its previous mistakes and change its strategy, making it much more reliable for complex tasks that take many steps to solve.

\subsection{Big-Picture Navigation via Agent Summaries}
Instead of trying to fit every line of code into the agent's memory, we use the \texttt{code\_index} to provide a high-level map. When a repository is indexed by \texttt{store.py}, it doesn't just save the raw text of the files. Instead, it uses an \textbf{agent} to create an "intent summary" for every file. This summary is what the agent searches through first.

In the \texttt{CodeIndex} model, the \texttt{summary} field is the primary search target. This approach solves the problem where agents get "lost" in large projects because they can't see the big picture. By searching these one-sentence summaries, the agent can understand the architecture of a 100-file project without ever having to read every single line. For instance, the agent can find the exact file related to "user authentication" just by searching the summaries. This keeps the agent's context window small and efficient, as it only loads the full code of the files it knows are relevant. This "summary-first" approach allows Contextware to scale to very large repositories without slowing down or hitting token limits.

\subsection{Environmental Reactivity and Staleness Detection}
A final insight we integrated is the need for the agent's memory to be "reactive" to changes in the project. If the agent remembers a version of a file from two weeks ago, but the developer changed that file yesterday, the agent will make mistakes based on outdated information. Contextware solves this by tracking the "last modified" time (\texttt{mtime}) of every file in the \texttt{code\_index} table.

Whenever the agent looks up a memory in \texttt{recall.py}, our system performs a real-time check. It compares the \texttt{last\_modified} timestamp stored in the database with the current timestamp on the hard drive using \texttt{os.path.getmtime}. If the file on the disk is newer than the memory, the system adds a \texttt{[STALE]} tag to the result. This tells the agent that its memory is out of date and it needs to re-read the file. This ensures the agent is always working with the most recent version of the code, which is a critical requirement for any real-world engineering tool. This hybrid approach—combining fast database searches with live file checks—is what makes the agent's memory robust and trustworthy.

\section{Implementation}

The implementation of Contextware is centered around a suite of specialized Python scripts that manage the entire lifecycle of an agent's memory. We use the \texttt{uv} tool to execute these scripts, which allows us to define dependencies directly in the script headers using PEP 723 metadata. This ensures that every time a script like \texttt{store.py} or \texttt{recall.py} runs, the correct versions of libraries like \texttt{lancedb} and \texttt{fastembed} are available in an isolated environment without any manual setup from the user.

\subsection{Data Modeling and Schema Definition in \texttt{db.py}} The foundation of the system is the database layer, defined in \texttt{db.py}. We use \textbf{LanceDB}, a local-first, serverless vector database that stores data in a columnar format on the user's hard drive. To interact with the database, we use the \texttt{LanceModel} class from the \texttt{lancedb.pydantic} library. This allows us to define our memory "buckets" using strict Python types, ensuring that the data saved by the agent is always structured and valid.

We have implemented three primary tables, each with a specific schema:
\begin{itemize}
   \item \textbf{Facts Table}: This table uses the \texttt{Fact} model. It contains a \texttt{content} string for the actual fact, a \texttt{timestamp} string (stored in ISO format), and a \texttt{vector} field. The vector is a \texttt{List[float]} with a fixed size of 384. This size is determined by our chosen embedding model.
    \item \textbf{Episodes Table}: This table uses the \texttt{Episode} model to track historical tasks. It includes fields for the \texttt{goal}, the \texttt{result} (which is a string restricted to values like "success" or "failure"), a \texttt{category} for filtering (like "refactor" or "bugfix"), and a narrative \texttt{summary}. The embedding vector for this table is generated by combining the goal and the summary into a single string.
    \item \textbf{Code Index Table}: This is the most complex table, using the \texttt{CodeIndex} model. It stores the \texttt{file\_path} as an absolute path to ensure the agent can find the file regardless of where the CLI is running. It includes a \texttt{summary} generated by an agent and a \texttt{last\_modified} float which stores the file's "mtime" from the disk. Most importantly, it has a \texttt{metadata} field that stores a dictionary of class names, method names, and top-level function signatures.
\end{itemize}

The \texttt{setup\_db} function in this script handles the initialization. It checks if a folder named \texttt{.lancedb} exists in the project root. If not, it creates it and initializes the three tables with their respective schemas. This process is automatic and happens the first time any Contextware command is run.

\subsection{Code Ingestion and Filesystem Crawling in \texttt{store.py}}
The \texttt{store.py} script is responsible for moving information from the project files and the agent's thoughts into the database. It begins by crawling the project directory. We use the \texttt{os.walk} function to visit every folder, but we have built-in logic to ignore noise. The script explicitly skips hidden folders like \texttt{.git}, \texttt{.venv}, and \texttt{\_\_pycache\_\_}. It also filters for specific file extensions, focusing on \texttt{.py}, \texttt{.md}, \texttt{.txt}, and \texttt{.json} files to ensure the index stays relevant to development work.

When a file is identified, the script performs a "Staleness Check" before doing any work. It looks up the file path in the \texttt{code\_index} table. If the file is already in the database and its \texttt{last\_modified} timestamp matches the one currently on the disk, the script skips that file to save time and tokens. If the file is new or has been changed, it proceeds to the static analysis and summarization phase.

\subsection{Static Analysis with the \texttt{SymbolVisitor}}
To understand the structure of Python files, \texttt{store.py} uses the \textbf{Abstract Syntax Tree (AST)} module. We implemented a custom class called \texttt{SymbolVisitor} that inherits from \texttt{ast.NodeVisitor}. This class "walks" through the parsed code of a Python file and identifies logical components.

When the visitor hits an \texttt{ast.ClassDef} node, it records the name of the class and enters a new "scope" to find its methods. For every \texttt{ast.FunctionDef} or \texttt{ast.AsyncFunctionDef} node it finds, it extracts the function name and the list of arguments. It also looks for docstrings (the text inside triple quotes) to provide more context for what the function does. All of this information is collected into a nested dictionary. This "Symbol Map" allows the agent to know, for example, that a file contains a class called \texttt{DatabaseManager} with a method called \texttt{connect(host, port)} without having to read the entire file.

\subsection{Agent-Driven File Summarization}
After the structural symbols are extracted, the script uses an \textbf{agent} to generate a high-level summary of the file. To stay within context and token limits, we don't send the entire file to the agent if it is very large. Instead, the script reads the first 4,000 characters of the file. This is usually enough to capture the imports, theclass definitions, and the initial documentation, which provides the most "intent" for the file.

The agent is given a specific system prompt: "You are a professional code indexer. Based on the provided code snippet, write a one-sentence summary of the file's primary purpose and its main exports." The resulting summary is then saved in the \texttt{summary} field of the \texttt{CodeIndex} record. This process runs in the background, allowing the project to be indexed progressively as the agent works.

\subsection{Local Embedding Generation with FastEmbed}
To turn these summaries, facts, and episodes into searchable vectors, we use the \textbf{FastEmbed} library. We specifically selected the \texttt{bge-small-en-v1.5} model. This model is highly optimized for CPU performance, which is a critical detail of our implementation. Most vector-based AI tools require a powerful GPU, but Contextware is designed to run on a standard developer's laptop without slowing down their other work.

When \texttt{store.py} has finished collecting data for a batch of files, it passes the text to the \texttt{model.embed()} function. This turns each piece of text into a 384-dimensional vector. These vectors are then "flushed" to the LanceDB tables in a single operation. This batching logic is important for performance; it is much faster to save 50 records at once than to save one record 50 times.

\subsection{Search and Retrieval Logic in \texttt{recall.py}}
The \texttt{recall.py} script handles the "Memory Reading" phase. When the agent wants to find information, it provides a query string and a target "bucket" (facts, episodes, or code). The script first turns the agent's query into a 384-dimensional vector using the same FastEmbed model used during the ingestion phase.

It then uses LanceDB's \textbf{Vector Search} capabilities to find the most similar records. The search uses "K-Nearest Neighbors" (KNN) logic to find the records whose vectors are closest to the query vector in the 384-dimensional space. We have tuned the script to return the top 5 most relevant results for each search.

\subsection{The Final Validation and Output Formatting}
Before the search results are returned to the agent, \texttt{recall.py} performs a final layer of validation. For every result from the \texttt{code\_index}, the script checks the file on disk one last time. If the file has been edited since it was last indexed (meaning the disk \texttt{mtime} is newer than the database \texttt{last\_modified} value), it prefixes the result with a \texttt{[STALE]} label. If they match, it uses a \texttt{[FRESH]} label.

The results are then formatted into a clean, Markdown-style text block. This block includes the file path, the agent-generated summary, the symbol map (classes and functions), and the staleness status. This formatted block is what the Gemini CLI provides back to the agent's context window. This ensures the agent is never just guessing; it has a verified, structural map of the project that it can rely on to make better decisions.

\section{Analysis}

\section{Future Directions}
While Contextware provides a robust foundation for persistent agent memory, several promising avenues for future research remain.

\subsection{New Benchmarks: Longitudinal and Lifecycle Performance}
Current benchmarks like \textbf{SWE-bench} are fundamentally stateless, evaluating an agent's ability to fix a single bug in isolation. However, real-world engineering is a longitudinal process. A critical future direction is the development of benchmarks that test an agent's performance on the same codebase over a sequence of patches and timesteps. This would allow us to measure the "Memory Dividend"—the degree to which an agent becomes faster and more accurate as its semantic memory of the project grows.

\subsection{Multi-modal Expansion: Screenshot-based Memory}
Modern software development involves visual feedback, particularly in UI/UX tasks. A future iteration of Contextware could incorporate \textbf{Screenshot-based Memory}. By capturing and indexing visual states during the development process, the agent could "remember" what the UI looked like before a specific change, enabling it to detect visual regressions or reason about layout issues using multi-modal context.

\subsection{Structured Graphs for Multi-Hop Reasoning}
While vector-based retrieval is excellent for similarity, it struggles with relational dependencies. We plan to transition the \texttt{code\_index} from a flat vector store to a \textbf{Knowledge Graph (KG)}. By representing files, classes, and functions as nodes and their calls/imports as edges, the agent can perform "multi-hop" traversals to understand the impact of a change across the entire dependency graph, solving the "relational blindness" of pure embedding-based systems.

\subsection{Memory in Multi-Agent Environments}
As development moves toward teams of specialized agents (e.g., Security, Testing, Feature agents), the management of \textbf{Shared vs. Private Memory} becomes paramount. Future work will explore "Hive Memory," where agents share a common semantic pool of architectural facts but maintain private episodic memories of their specific sub-tasks. This would prevent contextual noise while ensuring all agents adhere to the same project standards.
